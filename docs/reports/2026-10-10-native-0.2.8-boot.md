# Boot 0.2.8 — le CP ne fetche pas : SCRATCH_REG0 illisible

## Verdict matériel observé : le détail stage 16 nomme le coupable

Au boot du **10 octobre 2026 à 19:06:44 UTC** (21:06:44 local), `Navi48Native`
**0.2.8**, UUID **DBD6962B-7594-3B64-9B1A-BAAEAFC07D03** (conforme au build
déployé), cinq arguments natifs conformes :

- **Service conservé** : nœud présent, **1 instance**, `childPublished` à
  **19:06:55 UTC**. Adoption RW, DMA, firmware : tous OK comme en 0.2.7.
- **Sous-étape exacte** : `Stage16Step=5` (**`RingTest`**),
  `ComputeResult=0xE00002D6` (`Timeout`), `FailedStage=16`.
- **Preuve ring-test** : `RingTestPassed=0`, `FetchProven=0`,
  `RingTestValue=0xFFFFFFFF` (`UINT32_MAX`).
- `HardwareTouched=1`, `FirmwareLoaded=1`, `ResourcesRetainedUntilReboot=1`,
  `StartReturn=0` (service gardé, comme prévu).

**`RingTestValue=0xFFFFFFFF` signifie que `SCRATCH_REG0` (GC) est illisible :
le bus retourne tous-1 quand le registre ne répond pas.** Ni l'écriture CPU
initiale (`0xCAFEDEAD`) ni le packet CP (`0xDEADBEEF`) n'ont pris. Le CP ne
peut pas exécuter si le CPU lui-même ne peut pas écrire ce registre GC.

## Ce que ça exclut et ce que ça désigne

- **Exclu** : le chemin mémoire EOP (on n'y est jamais arrivé, step 6 non
  atteint), le ring lui-même (doorbell/wptr ont été programmés sans erreur),
  les firmwares et les stages 2–15 (tous passés, comme en 0.2.7).
- **Désigné** : l'accès au bloc GC via `GC base[1] + 0x2040`. Les accès MMIO
  de base (RCC, MMHUB, doorbell, config) marchent ; ce registre GC précis ne
  répond pas. Hypothèses compatibles, sans preuve supplémentaire : base GC
  incorrecte (discovery), GC en power-gate, ou horloges GFX coupées à ce
  stade. Ce n'est pas une preuve d'une de ces causes : c'est le prochain
  point à instrumenter (lire la base GC résolue + l'horloge/power avant le
  ring-test, sans écrire).
